# Link — Project Context

## Что мы создаём

**Link** — персональный Windows desktop companion и системный слой между пользователем, компьютером, проектами и AI.

Главная продуктовая идея: пользователь работает в Unreal, Blender, IDE, игре, браузере или другом приложении и не должен уходить из него в большое окно ChatGPT ради каждого вопроса. Link висит маленьким overlay поверх рабочего процесса, понимает активный проект и текущую задачу, по запросу получает контекст экрана/clipboard/voice/current app, отправляет его в связанную AI-беседу и возвращает ответ обратно в Link.

**UI для пользователя — Link. Браузер, extension, WebView, API или другой транспорт — внутренняя реализация, которую пользователь в нормальном сценарии не должен замечать.**

Целевой UX:

```text
current app / screen / clipboard / voice
                 ↓
            Context Brain
                 ↓
                Link
                 ↓
        Chat Integration Layer
                 ↓
      existing AI conversation
                 ↓
             response
                 ↓
      Link overlay / TTS / action
```

Link должен ощущаться как маленький персональный «Jarvis» для ежедневной работы: быстро спросить, показать экран, уточнить ошибку, продолжить проектный разговор или позже выполнить локальное действие, не разрывая основной рабочий поток.

Название Link одновременно означает «связь» и является личной отсылкой к Link из Zelda. В продукте не нужно копировать визуальную айдентику Nintendo/Zelda.

## Product north star

Обычный сценарий должен выглядеть примерно так:

1. Пользователь работает в текущем приложении и не переключается из него.
2. Link уже знает активный проект и Current Task.
3. Пользователь пишет или говорит вопрос.
4. При необходимости Link добавляет screen / clipboard / current app / project context.
5. Link отправляет запрос в связанную AI-беседу.
6. Ответ возвращается в overlay.
7. Пользователь продолжает работу в исходном приложении.

Браузер не является частью пользовательского workflow. Если browser-based transport используется внутри интеграции, он может быть запущен или свёрнут в фоне, но Link не должен требовать от пользователя вручную переключаться в него для обычного обмена сообщениями.

В долгосрочной перспективе Link должен не только разговаривать с AI, но и связывать AI с локальными действиями на ПК, project memory, command palette и автоматизацией.

## Основные продуктовые принципы

- Windows-first.
- Быстрый старт и низкое потребление ресурсов.
- Link — маленький floating companion, а не полноразмерный desktop chat client.
- Пользователь должен оставаться в текущем рабочем приложении во время обычного общения с AI.
- Local-first там, где это разумно: настройки, память проектов, скриншоты, голосовая предобработка, команды.
- Не отправлять экран/микрофон постоянно без явного режима пользователя.
- Chat integration / transport должен быть заменяемым; приложение не должно быть жёстко связано с одной моделью, провайдером или способом доставки.
- По возможности использовать существующие пользовательские AI-чаты и подписку вместо обязательного отдельного API-бюджета.
- Browser automation не должна проникать в core-модель Link: browser bridge, API, local model и другие способы связи должны быть адаптерами вокруг общего request/context слоя.
- Контекст должен быть видимым и управляемым: пользователь должен понимать, что именно Link отправляет в запрос.
- Простота важнее overengineering. Фичи добавляются этапами.

## Ключевые функции

### 1. Overlay
- Полупрозрачное borderless окно.
- Always-on-top.
- Компактное состояние, которое не мешает работе.
- Перетаскивание.
- Настраиваемая прозрачность.
- Click-through в неактивном состоянии.
- Быстрое раскрытие/скрытие по глобальному хоткею.
- System tray.
- В дальнейшем — компактное отображение AI-ответа без необходимости открывать браузер.

### 2. Vision
Link должен уметь по команде пользователя получать:
- весь экран;
- все мониторы;
- активное окно;
- выделенную область;
- при необходимости последние локальные снимки для сравнения.

Экран не должен постоянно отправляться куда-либо без явного режима.

Долгосрочная цель — current screen/current app context должен делать AI значительно полезнее, чем обычный отдельный чат: пользователь может спросить «что здесь не так?» или «что мне делать дальше?» без ручного переноса информации между приложениями.

### 3. Voice
- Push-to-talk по глобальному хоткею.
- Все хоткеи переназначаемые.
- Русский, английский и auto language.
- Core speech stack должен работать локально и без поминутного лимита.
- GPT остаётся intelligence layer: reasoning, search, screenshots, project context и linked chat не переносятся в отдельный voice provider.
- Целевой input: live partial STT → локальный Whisper final correction.
- Целевой output: local TTS с interrupt/barge-in.
- Нужны режимы Text / Voice Reply / Conversation.
- В Conversation Mode финальная voice-реплика автоматически отправляется обычным `PromptRequest`, поэтому screenshots/current app/project context продолжают работать.
- Транскрипт успешной voice-сессии является user text и не должен повторно отправляться как отдельный voice context.
- Полный принятый план: [docs/VOICE_CONVERSATION_PLAN.md](docs/VOICE_CONVERSATION_PLAN.md).

### 4. Projects
Пользователь выбирает активный проект, например:
- Big Steps / Zelda-like;
- рабочий проект;
- английский;
- другие проекты.

У проекта могут быть:
- связанные AI-чаты;
- project memory;
- decisions;
- open questions;
- current task;
- chat summaries;
- локальные файлы/папки;
- настройки контекста.

Проект должен позволять связать рабочий контекст Link с конкретной долгоживущей AI-беседой, чтобы пользователь мог продолжать существующий разговор из overlay.

### 5. Context Brain
Контекст разделяется на уровни:

GLOBAL
→ PROJECT
→ DECISIONS
→ CURRENT TASK
→ RELEVANT CHAT SUMMARIES
→ LIVE SCREEN / CLIPBOARD / APP

Link не должен отправлять всё подряд. Context Router выбирает только релевантные части.

Пользователь должен видеть Context Stack и иметь возможность исключить отдельные элементы перед отправкой.

### 6. Persistent AI conversation bridge
Link должен уметь общаться с существующей AI-беседой, не заставляя пользователя открывать её UI поверх рабочего приложения.

Core flow:

```text
PromptRequest
→ IChatIntegration / equivalent boundary
→ transport adapter
→ existing conversation
→ assistant response
→ Link overlay
```

Возможные transport adapters:
- browser companion / extension;
- direct provider API;
- local model;
- другие поддерживаемые интеграции.

Первый transport может использовать браузер в фоне, но обычный пользовательский сценарий не должен требовать:
- ручного перехода в браузер;
- ручного copy/paste каждого запроса;
- ручного получения ответа из чата.

Сам browser UI не является интерфейсом Link.

### 7. Chat handoff / compaction
Link должен помогать переносить работу между длинными чатами.

Нужны режимы:
- Full;
- Compact;
- Tiny.

Handoff должен сохранять:
- цель;
- важные правила проекта;
- уже сделанное;
- решения;
- текущий статус;
- следующий шаг;
- открытые вопросы.

В будущем — объединение контекста нескольких чатов.

### 8. Decision Memory
Решения хранятся отдельно от обычных summary, чтобы важные проектные договорённости не терялись при очередном сжатии.

Пример:
- принятое решение;
- дата/источник при необходимости;
- статус active/deprecated.

Отдельно хранить Open Questions.

### 9. Clipboard / Current App context
Link может использовать по явному действию или настройке:
- clipboard;
- название активного процесса;
- заголовок окна;
- выделенный текст;
- файлы.

Current application context — важная часть будущего «Jarvis»-сценария: Link должен понимать, с чем пользователь работает прямо сейчас, не заставляя его объяснять это вручную в каждом сообщении.

### 10. Command Palette / Actions
По аналогии с сильными сторонами Raycast:
- единая command palette;
- запуск приложений;
- открытие файлов/папок/ссылок;
- пользовательские quick commands;
- Script Commands через PowerShell/Python/EXE;
- позже — безопасные локальные действия голосом.

Локальные простые действия не должны требовать AI.

## Предварительный стек

Сейчас:
- C#;
- .NET 10;
- WPF;
- Windows native APIs;
- `Whisper.net` для final STT: Base на CPU и large-v3-turbo q5_0 на GPU через `Whisper.net.Runtime.Vulkan` (turbo скачивается и прогревается в фоне, если Vulkan-сборка загрузилась и whisper.cpp подтвердил GPU; иначе Base);
- `org.k2fsa.sherpa.onnx` 1.13.8 для live-черновика (streaming Zipformer RU/EN) и Silero VAD v5; сборка win-x64 через `RuntimeIdentifier`, чтобы не копировать нативные библиотеки девяти платформ.

Принятый voice roadmap:
- `sherpa-onnx` как единый local runtime для streaming ASR (сделано), Silero VAD (сделано), local TTS и при необходимости speech enhancement;
- `Whisper large-v3-turbo` как final correction — сделано (Phase 2, на GPU; на CPU 13,7 с на фразу, поэтому там остаётся Base);
- Supertonic 3 через sherpa-onnx как первый кандидат на локальный RU/EN TTS;
- Windows native audio playback с interrupt;
- cloud speech providers допускаются позже только как optional adapters, не как обязательная зависимость.

Позже, когда появится реальная потребность:
- SQLite для локальной памяти;
- Windows Graphics Capture для vision;
- browser companion/extension на TypeScript для поддерживаемых пользовательских интеграций.

Не добавлять эти зависимости заранее без реализуемой фичи.

## Архитектурные границы

Даже если пока существует один .NET project, логически разделять:
- Presentation/UI;
- Application state / use cases;
- Windows integrations;
- Capture;
- Voice;
- Projects/Context;
- Chat Integration adapters;
- Commands.

`PromptRequest` и Link context model принадлежат самому Link. Конкретные способы связи с ChatGPT/API/browser/local AI должны находиться за adapter boundary и не протекать в основной UI/context код.

Не создавать отдельные assemblies только ради «чистой архитектуры», пока размер проекта этого не требует.

### Milestone 4 — Persistent AI Conversation Bridge
Статус: текстовый end-to-end сценарий работает у пользователя. Загрузка изображения дала конкретную ошибку `ChatGPT image input was not found`; расширение обновлено для открытия upload-контрола и ожидания preview, но требуется повторная ручная проверка на реальной вкладке.

Цель milestone: пользователь общается с существующей AI-беседой из Link и получает ответ обратно в overlay, не переключаясь в браузер.

Этапы:
- provider-neutral / transport-neutral `IChatIntegration` boundary — реализован;
- связь проекта с конкретной AI-беседой — реализована;
- browser companion и loopback transport — реализованы;
- отправка user text и clipboard — проверена; путь загрузки image context обновлён, ожидает проверки на реальном ChatGPT;
- получение streamed assistant response обратно в Link — реализовано;
- компактное отображение ответа в overlay — реализовано;
- ручная проверка обновлённого image upload, minimized/background и ответа на запрос с изображением — ожидается;
- браузер, если используется как transport, работает в фоне и не становится пользовательским UI;
- уровень ответа Fast / Normal / Deep — реализован: provider-neutral подсказка в запросе + переключение пикера режима в composer ChatGPT («Мгновенный» / «Средний» / «Высокий») с проверкой результата (companion 0.7.0); на реальном залогиненном ChatGPT ожидает ручной проверки;
- ответ восстанавливается как Markdown из DOM (код, списки, таблицы) — проверено на новом UI ChatGPT;
- отмена (Stop/Esc) доходит до вкладки и останавливает генерацию; запрос не может ждать вечно: 20 с без ответа вкладки или 45 с тишины во время ответа — ошибка; тихий запрос повторно предлагается вкладке каждые 10 с и подхватывается после перезагрузки страницы/расширения без повторной отправки prompt — реализовано и проверено тестами bridge (loopback HTTP) и companion (headless Edge).

Direct API integration остаётся возможным вторым adapter'ом, но не должна быть обязательным фундаментом продукта.

## Текущий статус репозитория

Реализована первая используемая локальная версия desktop companion:

- компактный auto-height frosted-glass overlay с завершённым collapsed state, tray и глобальными hotkeys;
- screen capture всех требуемых источников и локальный preview;
- push-to-talk, WAV и локальный RU/EN/Auto STT через Whisper;
- clipboard, видимый context stack, проекты и current task;
- canonical versioned `PromptRequest` для application и integration flow;
- browser ChatGPT integration через локальный loopback bridge;
- project-to-conversation linking, send/progress/response flow и response UI;
- `Enter` для отправки и `Shift+Enter` для новой строки; Stop/Esc отменяет запрос;
- уровень ответа Fast / Normal / Deep рядом со статусом чата;
- ширина overlay 320–1200 px (левый/правый край); высота всегда по содержимому, а нижний край задаёт предел роста (`WindowPlacement.HeightLimit`): длинный ответ заполняет выбранную высоту и скроллится, короткий остаётся компактным (решение пользователя — не растягивать короткий ответ); двойной клик по нижнему краю возвращает компактный default; collapsed capsule остаётся фиксированной;
- последний ответ хранится per-project (`LinkProject.LastResponse` с `ConversationId` связанной беседы) и показывается при `LoadProject/SwitchProject`; без ответа панель скрыта;
- глобальный hotkey Send (`Ctrl+Alt+Enter`) вызывает обычный send; во время записи/распознавания голоса отправка откладывается до готового транскрипта; во время активного request не работает как Stop;
- уведомление Windows (balloon через tray) о готовом ответе или ошибке, если Link скрыт или неактивен; клик открывает Link на проекте запроса; автопоказ Link по завершении ответа убран;
- latched work target (`CurrentApplicationService.WorkTarget`): фиксируется global hotkey'ем или возвратом в Link после ≥ 2 с работы в приложении; окна ChatGPT (по заголовку) неявно его не заменяют, собственные hide/show Link тоже; используется для metadata, Auto active window и Active window capture;
- один manual Region context: новый регион заменяет прежний, повторный вызов при открытом selector игнорируется;
- выбор и тест микрофона в Settings;
- голосовой ответ на продиктованный запрос голосом Windows (Settings → Voice replies: вкл/выкл, голос, скорость, тест); PTT во время речи перебивает и слушает, Esc/Stop/Send hotkey — замолкает;
- Voice Reply pass 2: ответ читается по мере streaming (`SpokenAnswerStream`: только законченные предложения из `ChatProgressState.Receiving`, без повторов, та же политика «первый абзац, до трёх предложений»; остаток и «Подробности на экране.» — на Completed); при ожидании > 6 с — один waiting cue на языке вопроса («Секунду.» / «Думаю над ответом.» / «Ещё немного.»), отменяется с первым Receiving; статуса «ищу в интернете» нет, bridge его не сообщает. Esc/Stop сначала заглушают речь, повторно — отменяют запрос; PTT во время streaming-ответа перебивает, дальше ответ не читается, а продиктованное остаётся в PromptBox как следующее сообщение (Send во время активного запроса не срабатывает);
- live voice draft (Voice pass 3, 2026-09-24): один waveIn-захват отдаёт PCM-блоки (`IAudioRecorder.SamplesCaptured`) в `IStreamingSpeechToText` → `SherpaStreamingSpeechToText`: Silero VAD v5 (порог 0.3 — сомнительное считается речью) и streaming Zipformer (RU — Vosk small int8, EN — icefall 20M int8; под Auto — язык прошлого транскрипта, сначала язык Windows). Черновик идёт в конец PromptBox (`PromptDraft`: набранный текст сохраняется, черновик заменяется, а не дописывается; поле read-only в Listening/Finalizing), после отпускания Whisper заменяет его финалом. Если VAD не услышал речи и черновик пуст — Whisper не запускается («No speech heard»). Распознаватель грузится ~2 с и держит ~75–100 МБ, поэтому кэшируется и выгружается через 10 мин без голоса; модели скачивает `SpeechModelManager` (один раз, проверка размера + SHA-256, закреплённые ревизии HF/GitHub), до загрузки статус «live text model is downloading». Settings → Voice: «Show my words while I speak». Whisper final pass — 8 потоков вместо 4 (−30% времени на 12-поточном CPU). Замеры: черновик RU точнее Whisper Base на синтетике; `WithOffset/WithDuration` в Whisper.net не обрезают аудио, поэтому VAD не тримит запись, а только гейтит;
- final STT (Voice pass 4, Phase 2, 2026-09-25): `SpeechToTextService` берёт Whisper large-v3-turbo q5_0 на GPU (Vulkan, ~0,25 с на фразу + ~0,8 с загрузка модели на RTX 4070 SUPER), пока его нет или нет GPU — Base на CPU. Turbo (574 МБ) скачивается и прогревается в фоне после первой диктовки; статус Finalizing показывает «Whisper turbo model is downloading (N% of 574 MB, once)» / «is warming up». Включается только после подтверждения GPU в логе whisper.cpp; при сбое на GPU фраза распознаётся Base, а turbo выключается до перезапуска;
- browser companion 0.5.0: ожидание ответа через MutationObserver вместо опроса каждые 250 мс; пока страница молчит (ChatGPT думает) — ничего не выполняется, пока меняется — взгляд ≤ раз в 150 мс и каждое изменение ответа уходит в LINK (0.4.0 слал ≤ 2 раз/с, пользователь заметил «прерывисто»); текст — только из markdown-корня ответа (никакого fallback на весь элемент, поэтому «Думаю»/«Thinking» и плейсхолдеры не становятся ответом); завершение — только при исчезнувшей Stop-кнопке и непустом ответе, по кнопкам действий хода (`copy-turn-action-button`) или `data-message-complete` сразу, иначе через 1.2 с тишины; в конце ответ перечитывается целиком. Режим ответа: с июня 2026 селектор ChatGPT стоит в composer (Instant / Medium / High / Extra High, по-русски «Мгновенный» / «Средний» / «Высокий»…); Fast/Deep перед каждым запросом читают текущий режим с кнопки и переключают на Instant / High, только если чат в другом (раньше LINK помнил «уже применено» и не замечал ручную смену на «Высокий»); Normal возвращает режим, который был до первого переключения LINK (`mode:<conversation>` в `chrome.storage.local`), иначе Medium/Auto; при неудаче статус перечисляет предложенные пункты. После перезагрузки расширения вкладку ChatGPT нужно обновить — иначе в ней работает старый скрипт (так и было с «ответа нет»). Проверено на mock-DOM, на реальном ChatGPT — пользователем;
- companion 0.6.0 и фоллбэк «Check chat» (2026-09-25): на 0.5.0 у пользователя ответ в режиме Fast/«Мгновенный» не дошёл до LINK, а страница «медленно набирала» текст; причина на реальном DOM не установлена — пользователь не дал доступ к вкладке. Поэтому: (1) взгляд на страницу ограничен формой composer и последними 4 детьми треда (тред = ближайший общий предок последних вопроса и ответа): на мок-чате в 19,5 тыс. узлов 0,002 мс вместо 2 мс, конвертация растущего ответа — не чаще 250 мс; (2) кнопки действий хода завершают ответ, даже если «Stop»-подобная кнопка залипла, а ответ без markdown-корня тогда читается целиком; (3) кнопка «Check chat» в шапке ответа шлёт `read`-запрос, который вкладка выполняет сразу, даже если ожидание зависло: ответ после последнего вопроса, флаг «ещё пишет» и диагностику селекторов → `link.log`; если вопрос дошёл до чата (`waiting`/`receiving`), мост завершает ждущий запрос готовым ответом; без запроса ответ показывается и сохраняется в проект; (4) LINK сам проверяет чат, если ждущий запрос 20 с ничего не слышал от вкладки (в лог — только когда ответ найден готовым). Следующий шаг по причине: прочитать диагностику из `link.log` после первого такого случая;
- companion 0.7.0 и устойчивый transport (2026-09-25). Причины, найденные в коде и воспроизведённые тестами на 0.6.0 (новые проверки против старого `content.js`/`background.js` дают 56 падений): (1) после Reload расширения новый service worker вызывал `discoverTabs(true)` дважды (верхний уровень и `onInstalled`) и инжектил `content.js` во вкладку дважды — две копии обрабатывали один запрос (повторная/пустая отправка, «already processing», вторая копия открывала пикер режима и тут же закрывала его, лишний клик Stop) — отсюда «после Reload нужен F5» и «запрос приходится отправлять несколько раз»; (2) Fast брал `model-switcher-dropdown-button` в шапке раньше пикера composer — он есть и у залогиненных (во встроенном браузере без логина: «Селектор модели», текст «ChatGPT»), поэтому «Высокий» не менялся; результат выбора не проверялся; (3) Stop-кнопка считалась без проверки видимости — скрытая Stop держала ответ вечно, ответ без markdown-корня не стримился и не завершался без кнопок хода; (4) bridge отдавал запрос вкладке один раз и после первого события ждал до 10 минут без контроля тишины, а при сбое доставки сразу давал ошибку. Что сделано: одна копия на страницу (`globalThis.linkCompanion`; копия перезагруженного расширения просит старые уступить через DOM-событие `link-companion-started`), handshake `link-hello` (версия, instanceId, беседа, занят ли) перед доставкой и раз в 15 с, починка вкладки — однократный инжект (single-flight на вкладку), `link-retire` для чужой версии, перезагрузка только недоступной страницы (discarded/crash/ошибка) и не чаще раза в минуту, никогда — живой страницы с уже отправленным prompt; bridge (`BridgeTimings`) переотдаёт запрос, о котором вкладка молчит 10 с (с `attempt` и `sent`; для отправленного — без картинок), 20 с без ответа вкладки или 45 с тишины — ошибка, отменённый/завершённый запрос отвечает вкладке 404 с `reason` (`cancelled` → Stop в ChatGPT, иначе вкладка тихо прекращает), события после конца не показываются; состояние запроса в `chrome.storage.local` (`request:<id>`: sending/sent, последний user message до него, id сообщения с prompt) и поиск prompt в чате по тексту — повторная доставка после перезагрузки страницы/расширения только подхватывает ответ. Ответ = последнее сообщение ассистента после сообщения с prompt; конец — кнопки хода (`…-turn-action-button`) даже при залипшем Stop, либо нет видимой Stop и ответ не меняется 1,2 с (без markdown-корня — 3 с и не строка статуса), либо `data-message-complete`, либо ответ и его ход не менялись минуту; «Думаю»/shimmer не стримятся. Пикер режима: кнопка с подписью режима в форме composer и до двух уровней выше, «Селектор модели» в шапке — только если в composer нет пикера; меню через `aria-controls`, после выбора — ожидание новой подписи на кнопке. LINK: состояния Reconnecting и Cancelled в шапке ответа, диагностика необычных завершений и ошибок из вкладки — в `link.log`. Производительность (headless Edge, реальное время): на чате 21 тыс. узлов стриминг 600 слов занимает главный поток одинаково с companion и без (в пределах шума), на 5 тыс. узлов — +~2%. Тесты: C# — bridge по loopback HTTP и Voice поверх bridge; JS — `tests/browser-extension` (мок ChatGPT, настоящие `content.js`/`background.js`, headless Edge с виртуальным временем, 25 сценариев), запускаются тем же раннером и в CI;
- ответ в overlay перерисовывается инкрементально: `RenderResponse` сравнивает Markdown-источник каждого блока с показанным и пересобирает только блоки с первого изменившегося, поэтому частые streaming-обновления не перестраивают весь `FlowDocument`;
- current application metadata и включаемый в Screen-меню Auto active window capture на каждый Send;
- обычные shortcut’ы через `RegisterHotKey`, low-level hook только для key-down/key-up push-to-talk;
- atomic JSON persistence и защищённый lifecycle активных screenshot attachments;
- `link.log` для неожиданных ошибок: после старта приложение предупреждает и продолжает работу, ошибка на старте показывает сообщение и завершает процесс.

Локальные данные хранятся в `%LocalAppData%\Link`. Код остаётся в одном WPF assembly и разделён на `Models`, `Services`, `Windows` и Presentation.

## Открытые проблемы (2026-09-25, после companion 0.7.0)

Проблемы из прошлой сессии (Fast не переключал «Высокий», готовый ответ не доходил до Link, после Reload расширения нужен был F5, запрос приходилось отправлять повторно, вечное «Waiting») исправлены в коде по найденным причинам (см. «companion 0.7.0» выше) и закрыты тестами на мок-DOM. Реальный залогиненный ChatGPT агенту недоступен (пользователь проверяет сам), поэтому остаётся подтвердить:

1. **Пикер режима на реальном UI.** Мок повторяет Radix-меню (открытие `pointerdown`, портал, `aria-controls`, пункты `menuitemradio`), как у меню «+» и «Селектор модели» без логина, но сам пикер «Высокий» залогиненного composer не видели. Если Fast не сработает, статус Link покажет «ChatGPT mode not switched (…)»: `mode picker not found` — кнопки с подписью режима нет в форме composer и двух уровнях выше; `the "…" picker did not open`; `Instant is not offered: …` со списком пунктов; `the picker still shows "…"`. По причине поправить `findModePicker` / `openMenu` / `MODES`.
2. **Конец ответа на реальном DOM.** Если признаки ChatGPT не сработают, ответ всё равно завершится (без видимой Stop — через 1,2–3 с, при залипшей Stop — через минуту), а в `link.log` появится строка `Chat completed: {"completedBy":…}` с тем, что видели селекторы (кнопки хода, Stop с видимостью, markdown-корни). Такие строки — повод уточнить селекторы; при обычном завершении лог пуст.
3. **Скрытая вкладка.** Если ChatGPT в фоновой вкладке дописывает текст в DOM только через `requestAnimationFrame`, ответ в Link может обрезаться на моменте, когда исчезла Stop, — проверить длинный ответ при свёрнутом браузере. Лечится только признаками ChatGPT (кнопки хода), companion текст не выдумывает.
4. **Производительность на реальном длинном чате** — на моках нагрузка companion в пределах шума; подтвердить, что при ожидании ответа ChatGPT не «набирает медленно».


## Следующая сессия — зафиксированные UX-задачи (2026-09-24)

Статус после UX pass 2026-09-24: пункты 1, 2, 3, 5, 6 реализованы (описание — в «Текущий статус репозитория»; пункт 6 закрыт вертикальным ресайзом, горизонтальный пользователь подтвердил рабочим). Для пункта 2 синхронизация ответов, написанных прямо в ChatGPT, не сделана: при появлении — лучше pull-запрос «последний assistant message» через bridge при переключении проекта, а не push в announce (у push-варианта гонки со свежим ответом Link). Пункты 4 и 7 (live voice и spoken assistant) отложены пользователем до отдельного обсуждения дизайна голосового режима.

Исходный список, замеченный пользователем на реальной версии:

1. **Region capture: не допускать несколько одинаково активных регионов.**
   - Сейчас каждый успешный `CaptureRegionAsync()` вызывает `AddScreenshot(result)`, поэтому несколько Region-capture накапливаются в `_context` и все уходят в следующий запрос.
   - Требуемое поведение: одновременно только один manual Region context. Новый успешно выбранный регион заменяет предыдущий Region screenshot.
   - Дополнительно нужен guard от повторного запуска `RegionSelectionWindow`, пока первый selector ещё открыт: повторный hotkey/click в этот момент просто игнорируется.

2. **Последний ответ должен быть project-scoped.**
   - Сейчас `_responseText` и ResponsePanel принадлежат `MainWindow`, а `LinkProject` не хранит последний assistant response. При `SwitchProject()` меняются task/connection, но остаётся ответ от прошлого проекта.
   - При переключении General / любого созданного проекта overlay должен показывать последний известный assistant response именно связанного чата этого проекта.
   - Минимальный первый вариант: сохранять последний ответ, полученный LINK, per-project и восстанавливать его при `LoadProject/SwitchProject`. Если bridge может надёжно прочитать последний assistant message из уже связанного чата, позже можно синхронизировать и сообщения, появившиеся вне LINK.

3. **Отдельный быстрый hotkey Send.**
   - `Enter` уже отправляет сообщение из PromptBox, `Shift+Enter` делает новую строку.
   - Нужен переназначаемый global shortcut `Send current prompt`, чтобы сценарий voice → release → send выполнялся без мыши и без необходимости переводить фокус в PromptBox.
   - Добавить action в `HotkeySettings`, Settings UI, `GlobalHotkeyService` и App dispatch. Во время активного request hotkey не должен случайно работать как Cancel/Stop.

4. **Live / partial voice transcription во время речи.**
   - Текущий Whisper flow транскрибирует только после `_audio.Stop()`: пока пользователь говорит, PromptBox не меняется.
   - Целевой UX: во время удержания PTT текст постепенно появляется в PromptBox; после отпускания выполняется финальная корректировка/финализация, без дублей.
   - Это не косметический UI fix: нужен streaming/partial STT слой поверх текущего waveIn PCM capture + Whisper, с throttling и безопасной заменой только текущего voice draft.
   - Финальный transcript остаётся обычным user text; raw audio не становится ContextItem.

Порядок следующего прохода: сначала Region dedupe + project-scoped response + Send hotkey как маленькие детерминированные UX-фиксы; затем отдельно сделать streaming voice, не ломая уже работающую запись/Whisper pipeline.

5. **Уведомление, когда AI закончил ответ.**
   - Если LINK скрыт/свёрнут или не активен, по завершении ответа нужен системный сигнал, чтобы пользователь мог отправить задачу, убрать LINK и продолжать работать.
   - Минимальный вариант без новой тяжёлой зависимости: tray notification / balloon через уже существующий tray service.
   - Более polished вариант позже: Windows App Notification (toast), клик по которому показывает LINK и нужный project response.
   - Не уведомлять, если LINK сейчас открыт и активен; ошибки/отмена могут иметь отдельный тип уведомления.

6. **Добавить вертикальный resize; горизонтальный уже работает хорошо.**
   - Пользователь подтвердил, что горизонтальное изменение ширины удобно и его не нужно переделывать.
   - Нужен ручной resize по нижнему краю: пользователь может увеличить/уменьшить высоту overlay.
   - После ручного vertical resize выбранная высота сохраняется и response area использует доступное место.
   - Collapsed mode остаётся фиксированным; horizontal resize 320–1200 px сохранить без изменений.

7. **Voice interaction / spoken assistant.**
   - Решение зафиксировано: core должен быть local-first и без лимита минут; GPT остаётся мозгом и продолжает получать screenshots/project/current-app context.
   - Live text: sherpa-onnx streaming ASR + Silero VAD; final correction: Whisper large-v3-turbo на GPU, Base на CPU (оба сделаны).
   - Voice output: `ITextToSpeech`, первый local candidate — Supertonic 3 через sherpa-onnx.
   - Нужны Text / Voice Reply / Conversation modes, auto-send after endpoint, честные waiting cues и PTT interrupt.
   - Во время долгого ожидания можно говорить «Секунду», «Думаю над ответом», «Получаю ответ», но не выдумывать web-search activity.
   - Полный implementation plan и state machine: [docs/VOICE_CONVERSATION_PLAN.md](docs/VOICE_CONVERSATION_PLAN.md).
