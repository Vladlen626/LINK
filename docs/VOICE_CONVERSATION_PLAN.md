# LINK Voice & Conversation

Принятая архитектура голосового слоя (2026-09-24) и её статус.

## Решение

- **GPT остаётся мозгом.** Speech-слой отвечает только за слух, детекцию речи и голос. Reasoning, поиск, vision,
  память и история остаются в связанной беседе: голосовой вопрос — обычный `PromptRequest` со скриншотами, текущим
  приложением и проектом. ChatGPT Voice Mode не фундамент LINK.
- **Local-first без поминутной оплаты.** Облачные STT/TTS — только как опциональные адаптеры на ключе пользователя,
  бесплатные для обычного использования (Gemini TTS free tier); без ключа и при сбое всё работает локально.
- **Транскрипт — обычный текст пользователя**: не `ContextItem`; сырое аудио в GPT не уходит.

```text
голос → live-черновик → финальный Whisper → PromptRequest + контекст → GPT
→ письменный ответ в overlay → голос → следующий ход
```

## Режимы

- **Text** — обычная работа, без голоса.
- **Voice Reply** — push-to-talk, отправка вручную, Link читает ответ по мере прихода (до ~900 символов, код и таблицы
  — фразой «на экране»); полный ответ остаётся в overlay. *Сделано.*
- **Conversation** — hands-free: Listening → конец фразы по VAD → финальный текст → auto Send → Waiting → Speaking →
  снова Listening. *Сделано (v1, этап 3, 2026-09-30).*

| Модель | Где | Время | Результат |

| GigaAM v3 (sherpa, RU) | CPU | 0,3 с | «в Ангеле не светится, хотя включён» — теряет английские термины |
| large-v3-turbo q5_0 | CPU | 13,7 с | лучший текст, но слишком медленно |

Детали:
- Turbo (574 МБ) скачивается после первой диктовки и прогревается (шейдеры ~10–15 с один раз). Включается, только
  если whisper.cpp подтвердил GPU; без GPU и при сбое — Base на CPU. Модели качает `SpeechModelManager` один раз
  (размер и SHA-256, закреплённые ревизии). Отдельной настройки качества нет.
- С клавишей VAD только решает, запускать ли Whisper (сомнительное считается речью), и запись не обрезает: Silero
  местами недосчитывает речь, а `WithOffset/WithDuration` в Whisper.net аудио не обрезают. Hands-free запись
  обрезается спереди — от начала фразы по VAD минус 1 с (`IAudioRecorder.Stop(skip)`): иначе Whisper получал бы
  минуты ожидания, где он выдумывает слова.
- Live-распознаватель грузится ~2 с и держит 75–100 МБ, поэтому кэшируется и выгружается через 10 минут без голоса.
  Язык под Auto — язык прошлого транскрипта, в первый раз — язык Windows.
- Черновик идёт в конец поля (`PromptDraft`) и заменяется, а не дописывается; пока идёт диктовка, поле только для
  чтения.
- Голосовой ответ (`SpeechTextSanitizer` → `VoiceTextChunker`): весь ответ до ~900 символов, потом «Остальное — на
  экране.»; код и таблица — одной фразой «… на экране.», список — до 8 пунктов; URL, ссылки-сноски, разметка, стек-трейсы
  и эмодзи не читаются, длинный путь — только имя файла. Первая фраза короче 24 символов («Да.») ждёт следующую.
  Waiting cue — один раз после ~6 с тишины.
- Голос ответа (`TextToSpeechService`): части ответа уходят в голос сразу; пока одна звучит, следующая синтезируется
  (не больше одной вперёд — заглушённый ответ тратит максимум один запрос), накопившиеся части склеиваются в один
  запрос до 400 символов. Короткие повторяющиеся фразы кэшируются на сессию. Провайдер, который упал, пропускается:
  лимит — сколько велит Google (1–60 мин), сеть — 20–30 с, неверный ключ — до его замены; быстрая временная ошибка
  повторяется один раз. Если часть уже звучала, другой голос её не повторяет. Задержки — строки `[TTS]` в `link.log`.
- Gemini: Interactions API, `stream: true`, `audio/l16` 24 кГц, `store: false`; в запросе только текст, голос, язык и
  одна постоянная короткая `speech_metadata.style` (спокойно, дружелюбно, разговорно; темп — по настройке). Ключ — DPAPI
  в `gemini-key.bin`, не в `settings.json` и не в логе. Перед ответом Link заранее открывает TLS-соединение (без ключа).
  Звук Gemini бывает медленнее, чем играется (5 с речи за 6–7 с), поэтому его речь ждёт запас в 2 с
  (`ITextToSpeechProvider.Prebuffer` → `IAudioSegment.SetPrebuffer`): плеер ждёт его перед фразой, в том числе сразу за
  предыдущей, и после «пересыхания» устройства; у локального голоса остаётся запас плеера в 120 мс.
- Локальный голос: Supertonic 3 int8 (145 МБ, 10 голосов, 44,1 кГц), на Ryzen 5 5600 фраза готова через 0,35–0,7 с
  (RTF 0,12–0,25), в памяти ~300 МБ — грузится, когда ответ ожидается, выгружается через 3 минуты тишины.
- `VoiceSession` — единственный владелец голосового состояния (Idle → Listening → Finalizing → Sending → Waiting →
  Speaking); `MainWindow` только отображает.

### Conversation Mode v1

- Переключатель — метка **Conversation** под полем, Settings → Voice, хоткей `Ctrl+Alt+Shift+Space` (`Ctrl+Alt+буква`
  заняты в IDE, а зарегистрированный хоткей отнимает сочетание у всех приложений). Настройка `ConversationMode`
  сохраняется; выключенный режим микрофон не открывает.
- Цикл ведёт окно: когда `VoiceSession` в Idle, запроса нет, Settings закрыт и курсор не в поле ввода, окно вызывает
  `StartHandsFree()`. Hands-free детектор: Silero с порогом 0,5 (открытый микрофон реагирует только на ясную речь),
  `MinSilenceDuration` 0,55 с, `MaxSpeechDuration` 60 с (по умолчанию 5 с — длинная фраза резалась бы на первом
  вдохе). Закрытый сегмент = конец фразы → `PhraseEnded` → сигнал `Heard` → Whisper → `SendAsync` выбранным
  маршрутом (Chat или Direct; Agent голосом не запускается никогда — только карточкой этапа 4). Окно запоминает
  приложение на переднем плане как рабочее, как при хоткее.
- Пока идёт запрос и пока Link говорит, микрофон закрыт; push-to-talk перебивает ответ, а во время hands-free
  слушания забирает фразу себе (она кончается с клавишей); Send заканчивает фразу сразу. Кнопки Link (перенаправление,
  Listen, выжимка) и фокус в поле ввода закрывают hands-free микрофон, если фраза не начата. После 2 минут без речи
  слушание начинается заново — запись не растёт (её потолок — 5 минут).
- В Conversation ответ звучит всегда, в том числе на набранный вопрос и с выключенным Voice replies; waiting cue —
  как у голосового вопроса (одна фраза после ~6 с). В Chat запрос несёт подсказку `[Interaction mode: Conversation — …
  Start with a short, natural spoken answer of one or two sentences; details, steps and code come after it.]`
  (`PromptRequest.Conversation`, схема 5); в Direct — нет.
- Ошибка распознавания: транскрипт виден в поле, пока идёт запрос; **✎ Edit** под ответом возвращает вопрос в поле,
  Enter спрашивает исправленный текст из того же снимка (экран, вложения, окно), без новой диктовки и захвата.
- Hands-free анимации нет (открытый микрофон показывают рамка и кнопка Voice): слушание может длиться весь день, а
  каждый кадр layered-окна дорог.

Замеры (2026-09-30, Ryzen 5 5600; стенд подаёт звук блоками по 50 мс в реальном темпе, фраза — локальный голос Link,
4 с, «почему у меня материал в анриле не светится…»):

| Что | Результат |
|---|---|
| Конец фразы после последнего звука | 0,75 с при `MinSilenceDuration` 0,65 (гистерезис Silero и блоки по 50 мс) → 0,65 с при 0,55 |
| Начало фразы по VAD | 2,01 с при звуке с 2,00 с — запаса в 1 с хватает |
| CPU слушания (VAD + live-черновик, шум комнаты) | 3,8–5,3 % одного ядра и с клавишей, и hands-free — одна и та же работа |

Конец фразы → отправка = 0,65 с паузы + распознавание (строка `[Voice] … transcribed N ms after listening ended`) +
подготовка в Link (`Link N ms` в строке `[Chat]`); Whisper turbo на GPU — ~0,25 с работы и ~0,8 с загрузки модели на
каждую фразу. Отправка → первая фраза ответа — строка `[TTS] first words of the answer ready … ms after the request
began` плюс старт звука из `[TTS] playback started`. CPU Link целиком за время слушания пишет каждая строка `[Voice]`:
по ним hands-free сравнивается с удержанием клавиши на живой работе.

## Что осталось

1. **Задержка после первых недель.** Держать Whisper turbo загруженным, пока включён Conversation (−0,8 с на фразу,
   но ~1 ГБ видеопамяти рядом с Unreal и Blender), и вынести паузу конца фразы в настройки — по строкам `[Voice]`
   и отзывам.
2. **Скриншоты в Conversation** — тот же `PromptRequest`; Auto active window уже работает, рабочим окном становится
   приложение на переднем плане в конце фразы. Позже — захват по фразам вроде «посмотри экран», но явная настройка
   важнее эвристики.
3. **Polish (Phase 8, только после реального использования)** — speech enhancement (GTCRN/DPDFNet в sherpa-onnx,
   опционально: может испортить хороший микрофон), wake word, hands-free barge-in с эхоподавлением, Spoken Summary
   для очень длинных ответов, каталог голосов Gemini (`GET /v1beta/voices`, русские голоса), multilingual streaming
   ASR для Auto после замеров, повтор waiting cue раз в 8–15 с для очень долгих ответов (Deep), если одной фразы
   окажется мало.

## Правила

- Один захват микрофона на всех потребителей; не гонять полный Whisper каждые 200 мс ради псевдо-стриминга.
- Вслух не читать код, таблицы, URL, длинные списки и Markdown слово в слово: письменный ответ — источник правды.
- Waiting cues: не сразу после Send, не чаще раза в 8–15 с, без «ищу в интернете», если транспорт этого не сообщил;
  ошибки не маскировать.
- Пока Link говорит, автоматический open-mic выключен; push-to-talk перебивает мгновенно.
- Если Link говорит в Conversation Mode, голос уже служит уведомлением — toast не нужен.
- Настройки не перегружать: Voice input (язык, микрофон, live-текст), Voice output (когда говорить, голос, скорость,
  тест), Conversation (вкл., auto-send, waiting cues); пороги VAD не показывать.
- Модели — в `%LocalAppData%\Link\Models`, скачиваются по необходимости, не в Git.

## Критерий Jarvis-like v1

Пользователь работает в Unreal, Blender или IDE и не трогает браузер: говорит вопрос → видит live-текст → Link
понимает конец фразы → прикладывает нужный контекст → GPT думает и ищет как обычно → Link сообщает, если ожидание
долгое → показывает полный ответ → произносит короткий ответ → push-to-talk его перебивает → Link снова слушает.
