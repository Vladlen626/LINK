# LINK: куда уходят токены, команда или один агент, учится ли Link тратить меньше

Разбор 10.10 по просьбе пользователя: страх, что Link «много жрёт», вопрос, становится ли он со временем дешевле и
лучше, и когда запускать команду. Код прочитан, живые прогоны не запускались. Числа ниже — модель на замере от 30.09
(PROJECT_CONTEXT, п. 4–5), а не новый замер. Настоящие цифры по своей задаче теперь можно выгрузить: ⋯ → **Export for
analysis**.

## Коротко

- **Solo почти ничего не повторяет.** Правила, роль и «Read first» уходят только в первое сообщение новой сессии
  (`CliAgentProvider.StandardInput`), продолжение несёт лишь ваши слова. Дорого другое: каждый запрос агента
  пересылает всю сессию, и к концу задачи запрос весит 55–86k вместо 16k на старте. Кэш (~96 %) делает это в
  ~7 раз дешевле, но объём растёт квадратично с длиной задачи.
- **Команда дороже на малых и средних задачах.** Она окупается примерно от 4 шагов, то есть от ~55 запросов
  соло-работы. По окну подписки Claude она окупается уже от ~30 запросов, потому что Standard-шаги берёт Codex.
  Подробно — в разделе «Команда или один агент».
- **«Учится и тратит меньше» — правда наполовину.** Качество Link копит: проверенные уроки в skills, карту,
  провалы работников в `workers.json`, калибровку критика. Замкнутой петли по токенам нет: числа он пишет, но ни одно
  решение на них не опирается (раздел «Учится ли Link тратить меньше»).
- **Слабые места — в команде и арте, не в Solo.** Это сессия ведущего, которая растёт на каждом ревью; новая сессия
  критика на каждый вердикт; лишние skills в «Read first»; скрытый рост карты и skills. Раздел «Слабые места», T1–T9.

## Команда или один агент: модель

Монте-Карло: по 40 000 прогонов на размер, параметры случайны в своих диапазонах. Скрипт —
`.agents/skills/agent-token-review/team_vs_solo.py`: подставьте замеренные числа, и он пересчитает всё ниже.

**Привязка к замеру.** Вход задачи ≈ N·B + h·N²/2. При B = 16k (старт запроса), h ≈ 3k (рост за запрос) и N ≈ 27
запросов это даёт 1,6 млн входа на задачу — столько и было в замере (8,0 млн на 5 задач). Единица — «≈ токены»
`TaskMetrics`: свежий вход ×1, кэш ×0,1, вывод ×5, умноженные на цену модели относительно Opus.

**Допущения** (диапазоны, равномерно):

| Что | Диапазон |
|---|---|
| Вывод (с размышлением) на запрос | 0,6–2k; у ведущего и Strong на Deep — ×1,5–3 |
| Цена Codex (Standard) и Haiku (Light) к Opus | 0,3–0,7 и 0,15–0,3 |
| Доля соло-прогона на поиск дороги (чтение, поиск) | 25–40 % |
| Сколько запросов шаг тратит, чтобы заново найти дорогу; бриф шага | 2–6; 3–6k |
| Ревью ведущего | 1–3 запроса, diff 2–8k, холодный кэш в 0–50 % ревью |
| Успех части у Solo после его проверки; потеря на длинной сессии | 0,88–0,96; до 0,08 на 100 запросов |
| Успех шага с первого раза: Strong / Standard / Light | 0,86–0,95 / 0,70–0,90 / 0,60–0,85 |
| Потеря на передаче между сессиями | 0–0,08 |
| Ревью ведущего и проверка проекта ловят плохой шаг | 0,5–0,85 и 0,3–0,7 |

Провал шага разбирается так: redo в той же сессии, затем повторный провал, затем уровень выше. Плохой шаг, которого
никто не заметил, означает задачу «готово, но не так» — нужен ваш раунд.

**Итог по размерам** (ревью ведущего включено, как по умолчанию):

| Задача | Solo, ≈ ток. (медиана) | Команда / Solo, все токены | Окно Claude, команда / Solo | Верно без вас: Solo → команда |
|---|---|---|---|---|
| S: 12–20 запросов, 2 шага | 213k | 1,9× (дешевле в 1 % случаев) | 1,6× (10 %) | 84 % → 89 % |
| M: 30–50 запросов, 3–5 шагов | 744k | 1,3× (16 %) | 1,07× (42 %) | 67 % → 79 % |
| L: 70–110 запросов, 6–8 шагов | 2,7M | 0,85× (74 %) | 0,71× (90 %) | 44 % → 66 % |

**Порог окупаемости** (шаги ≈ запросы / 14):

| Запросов соло | 10 | 20 | 30 | 40 | 50 | 60 | 80 | 100 | 120 |
|---|---|---|---|---|---|---|---|---|---|
| Все токены, команда / Solo | 2,70 | 1,64 | 1,26 | 1,17 | 1,09 | 0,95 | 0,88 | 0,77 | 0,70 |
| Окно Claude, команда / Solo | 2,21 | 1,30 | 0,98 | 0,94 | 0,89 | 0,77 | 0,73 | 0,64 | 0,59 |

Без ревью ведущего команда дешевле: M — 0,91×, L — 0,57×. Зато верный результат она даёт реже, чем Solo: на M 59 %
против 67 %. Ревью — это то, что покупает качество.

**Что сильнее всего двигает цену команды** (ранговая корреляция с отношением команда / Solo на M):

| Фактор | Связь | Что значит |
|---|---|---|
| Effort ведущего на Deep | +0,31 | самый дорогой рычаг |
| Число запросов ревью | +0,25 | |
| Вывод на запрос | +0,25 | |
| Повторный поиск дороги в каждом шаге | +0,17 | |
| Цена Codex | +0,15 | |
| Холодный кэш на ревью | +0,14 | |
| Рост контекста за запрос | −0,20 | играет за команду: длинную сессию свежие сессии режут |

**Вывод.**
- Команда — это страховка качества и способ разнести работу по двум подпискам, а не экономия на малой задаче.
- До ~4 шагов дешевле Solo, лучше с Plan first: план на Deep, работа на Standard в той же сессии.
- С 6+ шагов команда дешевле и надёжнее по всем меркам.
- Если в задаче разные инструменты (модель → риг → движок), команда уместна при любом размере: там каждому шагу
  нужна своя роль и свои skills.

Сейчас Link предлагает команду уже при трёх пунктах списка в брифе (`TeamRunner.Suggests`). По модели при трёх шагах
команда дороже на 15–30 % всех токенов, а по окну Claude выходит примерно вровень (T7).

## Учится ли Link тратить меньше

**Что есть:**
- Training: урок попадает в skill только после экзамена на вашей задаче.
- Агенты по правилам дописывают карту и skills, а карта сократила поиск: замер 30.09 показал 15,1 → 11,7 млн входа.
- `workers.json`: работник, дважды провалившийся на виде шага, больше его не получает. Доказанный дешёвый работник
  (3+ сделано, ≤20 % провалов) подсказывается уровнем ниже.
- Критик калибруется вашими оценками экзаменов.
- Правила-экономы: `CompactRule` (свежая сессия вместо большой или остывшей), автокомпакт CLI на 450k, план
  заголовками в шаге, состояние ≤6k, свои ответы Link — на Light без MCP, effort по виду шага.

**Чего нет — петли по токенам:**
- `TaskMetrics` (токены задачи, команда против Solo) считает теперь только итог выгрузки; ни одно решение на него не
  опирается. `TeamSettings.Alternate` («по очереди команда и Solo, чтобы измерить») нигде не читается.
- `WorkerEvidence` считает сделано/провалено, а токены не считает. Понижение уровня `AutoLower` выключено по
  умолчанию (качество первым).
- `AutoEffort` поднимает effort после провала. Опустить следующий ход он может только по `link-next` агента, а после
  череды успехов сам не снижает.
- Карта и skills растут, а их размер никто не проверяет. Каждая новая сессия со временем становится дороже (T6).

Иначе говоря, датчики есть: токены каждого прогона, `TaskMetrics`, `workers.json`. Регулятора нет. Его можно
поставить (предложение П5), но решение за вами: экономия против качества.

Проверено, что оправдано:
- правила и роль не повторяются в продолжениях;
- хвост проверки ограничен 60 строками, возвратов не больше двух;
- hand-off и compact ограничены 6k;
- экзамен в новой сессии — суть метода;
- эскалация и Plan first — разовый сознательный промах кэша при смене модели.

Не определено:
- реальное время жизни кэша у Claude Code и Codex. Код считает 60 минут; если на деле 5, почти каждое ревью и redo
  после шага холодные, и T1–T2 весят больше;
- ломает ли кэш смена effort при продолжении (план на xhigh → ревью на medium);
- цена картинок у Codex;
- реальные `map.md` и skills в ваших проектах.

## Предложение: что сделать

По отдаче на строку кода:

| # | Что | Чинит |
|---|---|---|
| П1 | Ревью ведущего: `CompactRule` перед ревью, diff от начала шага, текст ревью один раз — **сделано** | T1 |
| П2 | Критик на redo — продолжение своей сессии, skills только `art-style` — **сделано** | T2 |
| П3 | `SkillsFor`: related только при счёте ≥2; шагам и критику — skills роли — **сделано** | T3 |
| П4 | `TeamRunner.Suggests` — с 4 пунктов; строка о пороге на карточке — **сделано** | T7 |
| П5 | Петля: в Stats строка «Solo против команды» по `TaskMetrics` (≈ токены и окно Claude на задачу по виду). Подключить `Alternate` (A/B по очереди). Подсказка `AutoLower` с цифрами | T8 |
| П6 | `CompactRule` для Promote и Back to | T5 |
| П7 | Бюджет размера карты и skills с задачей «condense» | T6 |
| П8 | Шаги подряд у того же работника — одна сессия | T4 |
| П9 | Мелочи | T9 |

П1–П4 — небольшие правки и тесты, с ними команда дешевеет сильнее всего. П5 даёт настоящие цифры вместо модели.

Как сделаны П1–П4:
- П1. Перед ревью `CompactRule.ForStep` смотрит сессию ведущего: у бюджета или остывшая — ревью в новой сессии с
  состоянием задачи (`TaskState.ReviewBrief`), без ожидания. Diff — прогона исполнителя: в git перед прогоном Link
  пишет снимок ожидающих файлов через свой временный индекс (`AgentChanges.SnapshotAsync`; индекс и файлы
  пользователя не трогаются), после замечаний — только переделка. Сессия, давшая вердикт, получает вместо
  `team-review.md` строку `TeamPlan.ReviewAgain`.
- П2. Повторный вердикт — в сессии того же критика (`TeamStep.CriticSession`), только новые кадры и сохранённые
  файлы, medium. `sheet.py` метит PNG листа; есть лист — уходит он, кадры путями (`ArtCritic.Attached`).
- П3. Related — от двух слов, имя пакета словом не считается; шаг со специалистом и критик читают только skills роли
  и дополнение игры к ним (`ProjectRoles.OwnSkills`: `blender-project` рядом с `blender-model`).
- П4. Команда сама — от двух специалистов или четырёх пунктов; у галки «pays off from ~4 steps».
