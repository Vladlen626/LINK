# LINK как харнесс: идеи по улучшению

Разбор материалов пользователя от 30.09.2026 (видео и репозитории ниже). Это идеи, а не принятые решения: после
согласования они идут в [AGENT_HARNESS_PLAN.md](AGENT_HARNESS_PLAN.md) и этапы из [`docs/stages/`](stages/).

## Цель

Хороший харнесс при бережном бюджете. Харнесс не делает модель умнее: он убирает из её работы поиск, навигацию и
повторные ошибки, чтобы токены уходили на задачу. Отсюда правило отбора: **каждый слой доказывает пользу замером на
настоящих задачах, иначе его убирают**. Это продолжает «Как думаем о харнессе» из
[этапа 5](stages/5-nori.md): мало инструментов, границы в коде, а не в тексте, один агент.

## Идеи по порядку пользы

Формат: что делаем → где в LINK → цена → как понять, что помогло.

### 0. Замер — основа всего остального

- **Что:** на каждую задачу агента одна строка `[Agent]` в `link.log` и сводка в Activity: токены или стоимость,
  число ходов, вызовов инструментов, из них поисков (grep/glob/чтений), ошибок инструментов, время.
- **Где:** парсеры событий (`ClaudeEventParser`, парсер Codex) уже видят `tool_use` и `tool_result`. У Claude Code
  итоговое событие `result` несёт usage, стоимость и число ходов; у Codex — usage в событиях хода (поля проверить).
- **Цена:** малая.
- **Зачем:** без этого пункт 5 этапа 5 («нужен ли слой») не проверить, а бюджет не видно.

### 1. Контекст за ноль токенов: рабочая папка

- **Что:** у проекта понятная структура и канон имён: путь говорит, что это (`exports/`, `renders/`, `scenes/`), нет
  `_v2`/`_final`. Корневой `AGENTS.md` — короткий: что где лежит и как проверить. Не раскладывать `AGENTS.md` по всем
  папкам: по материалам это вредит, их трудно держать в актуальном виде.
- **Prep:** кнопка в LINK запускает агента в Analyze один раз, он пишет короткую карту `docs/map.md` (или
  `domains/<домен>.md` для больших проектов). Дальше агент читает её вместо обхода папки. Обновление — той же кнопкой,
  когда карта устарела.
- **В Chat:** та же карта уходит в ChatGPT как текст проекта вместо скриншотов, когда вопрос про проект.
- **Цена:** малая, это skill и одна кнопка. **Мерить:** число поисков и чтений до первой правки.

### 2. Проверка готовности (`check`)

- **Что:** у рабочей папки одна команда проверки. Для кода — сборка, линтер, smoke-тесты; для Нори — рендер 3–5 кадров
  (уже в этапе 5). После Do LINK запускает её и возвращает вывод агенту до «готово» (продолжением той же сессии).
- **Не делаем:** отдельного агента-проверяющего: дорого и дрейфует.
- **Цена:** малая. **Мерить:** доля задач, где пользователь переделывал за агентом.

### 3. Контроль хода (детектор петель)

- **Что ловим по событиям:** один и тот же вызов с теми же аргументами N раз; одна и та же ошибка подряд; M поисков
  без единой правки; правка одного файла больше K раз.
- **Что делаем:** сначала только метка в Activity «похоже на петлю» и кнопки Stop или «Направить» с готовой подсказкой
  (перенаправление уже есть). Автоматическое вмешательство — только для малых моделей (п. 6) и только после замеров.
- **Перезапуск с чистого листа:** вместо продолжения в замусоренном контексте агент пишет короткую заметку о провале,
  LINK запускает новую сессию с задачей и этой заметкой. Это дешевле и чище, чем `--resume` с историей ошибок.
- **Цена:** средняя, это чистая логика над событиями без зависимостей. **Мерить:** доля задач с петлёй и токены в них.

### 4. Проверка действия до выполнения (путь как политика)

- **Что:** хук `PreToolUse` у Claude Code в рабочей папке блокирует заведомо провальный или опасный вызов и отвечает
  модели понятным сообщением: рекурсивный поиск по всему диску, запись в `.blend` без копии, выполнение кода в
  Analyze. `PostToolUse` может напомнить «перечитай файл перед следующей правкой».
- **Правило отбора:** правило появляется только после реального провала из `link.log`, не заранее. У Codex наличие
  хуков проверить; если их нет — только детектор LINK.
- **Цена:** малая на правило. **Мерить:** срабатывания хука и исход задачи.

### 5. Skills из провалов

- **Что:** после задачи, где агент ошибся и выправился, LINK предлагает записать урок одной-двумя строками в skill
  проекта. Пользователь подтверждает; молча не пишем.
- **Цена:** малая. Делать после п. 0–3, когда будет видно, какие провалы повторяются.

### 6. Дешёвые модели

- **Что:** третий раннер — opencode (бесплатные и малые модели) рядом с Claude Code и Codex.
- **Почему после остального:** по статье слои 3–4 почти не помогают сильным рассуждающим моделям и сильно помогают
  малым instruct-моделям. Значит, их польза и экономия бюджета видны именно здесь.
- **Бюджет:** простые задачи — Chat (подписка) или малая модель; сложные — Claude Code или Codex.
- **Цена:** средняя. **Мерить:** те же 5 задач этапа 5 на трёх раннерах.

### 7. Короткий вывод инструментов

- **Что:** если MCP или скрипт возвращает многословный JSON, завернуть в короткий CLI из skill (как `ue-tool.sh`). Для
  кодовых папок — рекомендовать AST/codegraph MCP вместо grep. Своего сервера не пишем.
- **Когда:** по замерам п. 0, если вывод инструментов занимает заметную долю токенов.

## Что не берём и почему

- larql — интерпретируемость локальных весов, к облачным моделям LINK не относится.
- Зоопарк агентов: оркестратор, дочерние агенты, отдельный проверяющий — дорого, дрейф проверки.
- `AGENTS.md` в каждой папке и журнал изменений в них — пока хватает `git log` по запросу.
- Автоматическая доработка харнесса Codex-ом по логам: по статье работает в детерминированных средах; у нас задачи
  открытые. Правила пишем руками из замеченных провалов.
- Virtual trees, TOON и прочие форматы — пока нет данных, которые их требуют.

## Предлагаемый порядок

1. Замер (п. 0) — в работу вместе с этапом 5, до сравнения «с харнессом и без».
2. Рабочая папка и Prep (п. 1) + `check` (п. 2) — входят в этап 5 почти без доработок LINK.
3. Детектор петель и перезапуск с чистого листа (п. 3) — отдельный этап 6 после замеров.
4. Хуки (п. 4) и skills из провалов (п. 5) — по мере реальных провалов.
5. Раннер opencode (п. 6) — когда п. 0–3 готовы и есть что сравнивать.
